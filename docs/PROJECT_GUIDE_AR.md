# شرح مشروع SaleeM وآلية عمله

## 1. ما وظيفة المشروع؟

SaleeM تطبيق ويب يحلل صورة شارت الذهب XAUUSD على فريم خمس دقائق. لا ينفذ صفقات ولا يتصل بحساب التداول. وظيفته قراءة السعر والمحور من الصورة، إضافة سياق السوق من أربعة فريمات، اختيار أقرب سيناريو، ثم إخراج صورة منظمة.

## 2. مسار الطلب من البداية إلى النهاية

```text
المستخدم يرفع صورة
        ↓
FastAPI يتحقق من النوع والحجم والأبعاد
        ↓
قص ذكي مؤقت لصندوق الشارت عند الحاجة
        ↓
Twelve Data: M5 + M15 + H1 + H4
        ↓
بناء ملخص حسابي للفريمات
        ↓
OpenAI يقرأ الصورة ويرجع JSON منظمًا
        ↓
التحقق البرمجي يصحح الاتجاه والمستويات والوقف والأهداف
        ↓
Renderer يرسم الطبقات فوق صورة الشارت الأصلية
        ↓
الصفحة تعرض الصورة والحفظ والمشاركة والتقييم
```

## 3. مصدر كل معلومة

| المعلومة | المصدر الأساسي |
|---|---|
| السعر الحالي وموضعه | صورة المستخدم |
| أرقام محور الأسعار | صورة المستخدم |
| الشموع والتوقيتات | Twelve Data |
| اتجاه H4/H1/M15/M5 | حسابات بيانات السوق |
| الدعم والمقاومة | مزيج من نموذج التحليل والشموع الفعلية |
| قرار الحالة | قواعد Python بعد نتيجة النموذج |
| شكل النتيجة | `app/engine/renderer.py` |

## 4. قواعد الاتجاه

- يحسب كل فريم اتجاهًا ودرجة ثقة من الحركة والبنية القريبة.
- H4 وH1 لهما الوزن الأكبر، ثم M15، ثم M5.
- نتيجة OpenAI تساهم في القرار، لكنها لا تستطيع وحدها فرض شراء أو بيع.
- توجد منطقة حياد حقيقية؛ عند ضعف الدرجة تكون النتيجة غير واضحة بدل اختراع صفقة.
- عند تعارض H4 وH1 تُخفض الثقة تلقائيًا.

## 5. حالات الصفقة الحالية

### مراقبة

تظهر عندما يكون الاتجاه غير واضح، أو الاحتمال أقل من 55٪، أو لا يوجد سيناريو فني واضح. تكون Entry عند السعر الحالي، ولا تظهر Cancel، ويبدأ منها سهمان متعاكسان.

### مشروط

يوجد اتجاه وسيناريو منطقي، لكنه يحتاج كسرًا أو إعادة اختبار أو شمعة تأكيد.

### مؤكد/نشط

يحتاج جميع الشروط التالية داخل الكود:

- احتمال 70٪ فأعلى مع اكتمال التأكيد.
- النموذج أعاد حالة «مؤكد».
- H4 وH1 في اتجاه الصفقة.
- توافق الفريمات 75٪ فأعلى.
- الوقف والأهداف في الجهات الصحيحة.
- لا توجد تحذيرات من مزود السوق.
- لا توجد مقاومة/دعم معاكس قوي قريب جدًا.

## 6. الدخول والوقف والأهداف

- الدخول يُختار من أقرب مستوى منطقي وليس السعر الحالي تلقائيًا.
- الوقف يُختبر أولًا كما اقترحه النموذج، ثم أقرب قاع/قمة في آخر خمس شمعات، ثم أقرب دعم/مقاومة.
- الحد الأدنى لمسافة الوقف 0.6 دولار، والحد الأعلى الديناميكي لا يتجاوز 4 دولارات.
- الأهداف تبدأ من الدعم أو المقاومة المقابلة. إن لم تكفِ، تُستخدم قيم النموذج ثم مضاعفات المخاطرة 1R و1.7R و2.5R وما بعدها.

## 7. محور الأسعار

المشروع يحاول بناء تحويل واحد من السعر إلى الموضع الرأسي. تستخدمه الشموع والبطاقات والمستويات والدخول والوقف والأهداف جميعًا. عند وجود قراءات واضحة متعددة يستخدم Exact Axis Mode، وعند نقصها يستخدم وضعًا احتياطيًا مع تنبيه بدل إيقاف التحليل.

## 8. التخزين والخصوصية

- صورة الرفع تُحفظ في ملف مؤقت وتحذف بعد الطلب.
- نتيجة الصورة تُعاد داخل HTML بصيغة Base64 ولا تُحفظ كملف دائم.
- بيانات السوق تُحفظ في JSON مؤقت أو على Railway Volume.
- التقييمات والملاحظات تُحفظ في ملف JSON منفصل إذا كانت ميزة التقييم مستخدمة.
- لا توجد حاليًا قاعدة بيانات أو حسابات مستخدمين.

## 9. نقاط القوة

- اختبارات جيدة تغطي المنطق والرسم والمحور: 52 اختبارًا عند فحص النسخة الأصلية.
- فصل واضح نسبيًا بين السوق والتحليل والرسم والواجهة.
- قواعد حماية تمنع الوقف والهدف في الجهة الخاطئة.
- تخزين مؤقت مستقل لكل فريم مع استخدام آخر بيانات صالحة عند تعطل المزود.
- JSON Schema صارم يقلل النتائج غير المنظمة من نموذج الذكاء الاصطناعي.

## 10. الديون التقنية الحالية

- `analyzer.py` و`renderer.py` كبيران جدًا ويجب تقسيمهما.
- توجد وحدات محرك فارغة مخصصة للمستقبل، لكنها لا تنفذ منطقًا حاليًا.
- توجد وظائف رسم قديمة غير مستخدمة؛ لا يُنصح بحذفها قبل اختبار بصري مقارن.
- أوزان الفريمات معرفة بصيغتين متقاربتين داخل التحليل ويجب توحيدها.
- الشرح في بعض المواصفات القديمة لا يطابق وضع Overlay الحالي.
- واجهة النتيجة طويلة وتخلط بين الاستخدام، الشرح الفني، التقييم، والإحصاءات.
- تخزين التقييمات في JSON مناسب لنسخة واحدة فقط، وليس لتعدد العمال أو التوسع.
- لا يوجد حد طلبات لمنع إساءة استخدام التحليل أو إرسال الملاحظات.

## 11. ترتيب التطوير المقترح

1. اعتماد «دستور واحد» نهائي للقواعد البصرية والتحليلية.
2. إعادة ترتيب الواجهة دون تغيير محرك التحليل.
3. تقسيم `analyzer.py` إلى: قراءة الصورة، قرار الاتجاه، المستويات، إدارة OpenAI، والتحقق.
4. تقسيم `renderer.py` إلى: محور، خلفية، مستويات، صفقة، مناطق، رأس وجلسات.
5. إضافة سجل تحليل تقني غير شخصي: مدة كل مرحلة، مصدر السعر، وضع المحور، وتحذيرات البيانات.
6. نقل التقييمات إلى SQLite أو PostgreSQL عند فتح التطبيق لعدة مستخدمين.
